# Персональный чек-лист для Code Review

Этот чек-лист используется при проведении ревью кода в проекте. Цель — обеспечить высокое качество кода, безопасность и поддерживаемость.

## 1.  Стиль и читаемость (Style & Readability)
- [ ] Код соответствует стандарту **PEP 8** (отступы, длина строк, пробелы).
- [ ] Имена переменных, функций и классов отражают их суть (используется `snake_case` и `PascalCase`).
- [ ] Нет «магических чисел» и строк — используются константы или конфигурационные файлы.
- [ ] Функции не слишком длинные (рекомендуется до 30-40 строк) и выполняют одну задачу.
- [ ] Нет закомментированного «мертвого» кода.
- [ ] Комментарии объясняют *почему* сделано именно так, а не *что* делает код (если код не очевиден).

## 2.  Логика и архитектура (Logic & Architecture)
- [ ] Бизнес-логика находится в слое `services`, а не в `blueprints` (контроллерах) или `models`.
- [ ] Работа с базой данных изолирована в слое `repositories`. Контроллеры не делают прямых запросов к БД.
- [ ] Корректно обрабатываются граничные случаи (пустые списки, `None`, деление на ноль, отсутствие записей в БД).
- [ ] Используются DTO (`dtos/`) для валидации входящих данных из запросов.
- [ ] Ошибки обрабатываются корректно (используются `try/except`, возвращаются правильные HTTP-статусы, например `400`, `404`, `500`).

## 3. Безопасность (Security)
- [ ] **SQL-инъекции:** используются параметризованные запросы или ORM (не допускается конкатенация строк в SQL).
- [ ] **XSS:** в HTML-шаблонах используется автоэкранирование Jinja2 (не используется `|safe` без острой необходимости).
- [ ] **CSRF:** формы, изменяющие состояние (POST/PUT/DELETE), защищены CSRF-токенами.
- [ ] **Аутентификация:** маршруты в `admin.py` и других файлах защищены декораторами проверки прав доступа.
- [ ] **Утечка данных:** в логи и ответы API не попадают пароли, токены и персональные данные.
- [ ] **Капча:** механизм `puzzle_captcha` корректно проверяется на стороне сервера.

## 4.  Тестирование (Tests)
- [ ] Для нового функционала написаны тесты (юнит или интеграционные).
- [ ] Тесты проверяют не только успешные сценарии (Happy Path), но и ошибки (авторизация, неверный ввод).
- [ ] Тесты изолированы друг от друга (используются фикстуры в `conftest.py` для очистки БД).
- [ ] В тестах используются моки для внешних сервисов или тяжелых операций.

## 5. Документация (Documentation)
- [ ] Сложные функции и классы (в `services` и `utils`) имеют докстринги (`"""..."""`).
- [ ] При добавлении новых зависимостей они внесены в `requirements.txt`.
- [ ] Если изменилась структура БД, обновлен файл `schema.sql` (или создана миграция).
- [ ] Если добавлена новая фича, обновлен `README.md` или файлы в папке `docs/`.
